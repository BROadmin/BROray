# BROray-01 — управление операциями через KeenDNS

## Статус

Код этапа 01 подготовлен, ревизия R4. Локальная проверка пройдена.
Это не релиз, не физическая приёмка Keenetic и не результат прогона всего BROray.
Изменения не устанавливают приложение, не публикуют артефакты и не меняют конфигурацию роутера.

## Исходная проблема и база

В аудите WebUI-3.1.1-r12c01 изменяющие запросы operations API через KeenDNS
получали 403 ORIGIN_REJECTED, а локальный сценарий работал. Исходный common.sh
принимает Origin только при совпадении с HTTP_HOST. При переписанном Host
легитимный внешний Origin этого условия не выполняет.

Исходный проверенный коммит GitHub main:
`b8aab47470d8a0cdee39be374c349723aac176e0`.
Обнаруженная локальная база разработки:
`725c53f3ae2077e9f1abb8db0129554abc59c320`.
Чтением локального файла подтверждён тот же исходный common.sh. Это не означает,
что всё локальное дерево повторно проверено: применение пакета отдельно требует
точного HEAD, чистого дерева, исходного хеша файла и ожидаемого blob web-publish.sh.
Локальные доработки подписок не заменяются исходниками из старого main.

Исходный Git blob common.sh: `13cc3374726705477338941da411c547619d908e`.

## Контракт проверки

1. Проверка HTTP-метода, действующей сессии и `X-BROray-Request: operations` сохраняется.
2. Принимается только один синтаксически корректный Origin http/https без пути,
   userinfo, query, fragment, пробелов, управляющих символов и списков значений.
3. При совпадении с Host сохраняется прежний контракт HTTP/HTTPS. Этот быстрый
   путь не читает Keenetic и не зависит от доступности KeenDNS или публикации.
4. При несовпадении разрешён только точный HTTPS Origin существующей публикации
   BROray, подтверждённой через неизменённый `broray_web_publish_status_json`.
   Проверяются enabled/consistent, отсутствие recovery, доступность KeenDNS,
   наличие валидного receipt и его точное совпадение с live-блоком публикации.
5. Внешний адрес обязан совпасть с именем и доменом из результата чтения.
   Регистр DNS-имени и стандартные порты браузерного Origin нормализуются.
   Порт внутри настроенного доменного имени недопустим, даже `:443`.
6. Forwarded, X-Forwarded-Host, X-Forwarded-Proto, Referer и похожие заголовки
   не создают доверия. Маски `*.keenetic.link` и списки произвольных доменов не добавлены.
7. Неоднозначный, отсутствующий или недоступный источник подтверждения приводит
   к 403, а отсутствие/симлинк нового модуля — к 503. Запрос не доходит до координатора.
8. Проверки JSON, размера тела, operationId и допуска операций сохранены.

## Чтение конфигурации и границы безопасности

Существующий read-only модуль вызывается в отдельной shell-подоболочке.
Его dispatcher внутри этой подоболочки допускает только две уже используемые
команды: `show ndns` и `show running-config`. Каждая ограничена `timeout -k 1 3`:
три секунды до TERM, ещё одна до KILL. Это предел команд, а не жёсткий предел
всего HTTP-запроса, который включает обработку JSON/файлов и действия координатора.

До входа в статус-функцию создаётся новый private workspace с umask 077.
Предсуществующий каталог или симлинк не переиспользуется. Очистка удаляет только
четыре ожидаемых файла чтения и этот каталог. Глобальные блокировки не удаляются.
Никакие write-команды Keenetic для проверки Origin не выполняются.

Существующие зависимости ash, awk, jq и timeout используются без новых пакетов.
Фильтр jq не использует test/match/sub/gsub и другие функции Oniguruma.
Обычные regex в awk допустимы и не требуют Oniguruma.

Это не универсальная настройка любого reverse proxy. Дополнительное разрешение
относится к собственной подтверждённой публикации BROray через KeenDNS.
Если ndmc или подтверждение публикации недоступны, внешний изменяющий запрос
остаётся запрещён; локальная ветка same-host продолжает работать. Такое
ограничение необходимо отдельно проверить в сценарии аварийного восстановления.

## Выполненная локальная проверка

81 именованный тест выполнен в каждом из трёх режимов:
BusyBox 1.37.0 ash + системные утилиты; ash + BusyBox awk/timeout и другие
используемые applets; dash. Везде 81 PASS. Это 81 сценарий в трёх окружениях,
а не 243 разных сценария.

Выполняются реальные изменённые shell-файлы. Только литерал /opt/broray в
тестовых копиях заменяется private временным корнем. Авторизация, чтение тела,
координатор и выдача publication-status представлены явными test doubles.
Поэтому тесты доказывают новую проверку Origin и её включение в CGI,
но не работу реального координатора, receipt-проверки, lighttpd/KeenDNS и сети.

Исходный common.sh на сценарии с переписанным Host воспроизводит 403;
новый common.sh в том же сценарии выдаёт 200. Для stop/cancel/recover
проверяется предусмотренный ответ 202 и точное действие в тестовом координаторе.

## Применение и сборка

Использовать готовый patch из пакета этапа, не генерировать исправление заново.
Применять только в отдельном чистом checkout/worktree разрешённого базового
коммита после проверки `apply_stage01.py --check --repo <repo>`.
Для внесения: `apply_stage01.py --apply --repo <repo>`.
Скрипт не делает commit, reset, install, push, публикацию или вызовы сети.
Повторное применение к точным уже внесённым файлам возвращает ALREADY_APPLIED.
При изменении базы, зависимости или исходного файла — остановка без перезаписи.

Существующий `tools/build_runtime_candidate.py` находится в корне проекта,
выше каталога implementation. Он собирает дерево runtime и заново считает
архивные SHA256SUMS; новый .sh попадает в сборку с режимом по правилам сборщика.
Исторические runtime/SHA256SUMS не выдавать за манифест нового кандидата.
Не запускать установку копированием одного common.sh без новой библиотеки.
Номер кандидата не назначен и кандидата этим этапом не собрано.

## Обязательная приёмка точных собранных байтов

На тестовом Keenetic проверить действующую авторизацию, доступ локально и через
KeenDNS, pause/resume/stop-background, затем целевые cancel/recover без
разрушения чужих операций. Проверить отказ чужому/отсутствующему Origin,
сохранение запрета OPTIONS/CORS, неизменность настроек HTTP Proxy и отсутствие
оставшихся временных каталогов. Изменённое состояние автоматики восстановить.

Отдельно проверить штатную сборку, включение обоих runtime-файлов, режимы,
манифест, полный существующий набор operations HTTP/coordinator regressions,
а также ограничение ожидания при занятом/недоступном ndmc. Эти пункты пока PENDING.
