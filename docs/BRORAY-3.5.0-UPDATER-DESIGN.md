# BROray 3.5.0 — проект механизма обновления

**Статус:** принято владельцем 2026-11-01 как направление. Служба удалённой поддержки отложена. Дополняет план «BROray 3.5.0 на Go: чистая установка и независимые модули» и заменяет в нём части Task 4 (updater) и Task 10 (пакет/установка), где они расходятся с этим документом.

## 1. Проблема, которую решаем

В 3.x обновление выполнял код, уже установленный на роутере. Каждая особенность старой версии становилась постоянным барьером: r02 не пропускает чужую платформу, у r14 нет minisign, r12 на legacy-платформе ждёт перезагрузку. Исправить старый код нельзя — он уже на роутерах. Кроме того, updater был частью обновляемой платформы и должен был останавливать сам себя.

**Принцип 3.5.0:** установленная версия отвечает только за то, чтобы безопасно скачать и запустить обновитель **целевой** версии. Вся логика обновления, миграции и ремонта принадлежит новому коду.

## 2. Компоненты

| Компонент | Где живёт | Что делает | Как меняется |
| --- | --- | --- | --- |
| Загрузчик (launcher) | `/opt/broray/launcher/` вне каталогов версий | скачать манифест → проверить подпись → скачать обновитель → проверить хеш → запустить | почти никогда; контракт ABI v1 заморожен golden-тестами |
| Обновитель (installer) | скачивается каждый раз во временный каталог | чистая установка, обновление, ремонт, снятие старого 3.x | с каждым релизом; это один бинарник для всех сценариев |
| Демон `brorayd` | `/opt/broray/versions/<v>/` | продукт | через обновитель |
| Данные и WebUI | отдельные подписанные артефакты | каталоги маршрутов, интерфейс | через обновитель, без смены кода |

Терминальная команда первой установки, кнопка WebUI и восстановление после сбоя запускают **один и тот же** обновитель. Если загрузчик когда-нибудь окажется сломан, терминальная команда остаётся рабочим путём ремонта.

## 3. Контракт загрузчика (ABI v1, заморожен)

1. Получить манифест канала (`stable` / `beta`) по фиксированной схеме URL; переопределение URL только из локального конфига, подписанного тем же ключом (для тестовых каналов).
2. Проверить подпись манифеста: minisign/Ed25519, список доверенных ключей встроен. Ротация: новый ключ вводится заявлением, подписанным действующим ключом.
3. Выбрать запись обновителя по `GOARCH` и минимальной версии ABI; проверить размер и SHA-256 после скачивания.
4. Проверить свободное место (`/opt` и каталог временных файлов) до скачивания; при нехватке — отказ без изменений.
5. Запустить: `broray-installer apply --abi 1 --from <версия|none> --state /opt/broray --channel <канал> --progress json`. Прогресс — JSON-строки в stdout, диагностика — stderr. Код выхода и последнее событие обязательны; обрыв ≠ успех.
6. Ничего больше. Загрузчик не знает о форматах данных, версиях модулей и миграциях.

Изменение контракта допускается только новой версией ABI; обновитель обязан поддерживать все ABI, встречающиеся у опубликованных загрузчиков.

## 4. Манифест канала

- `schemaVersion`, `channel`, `issuedAt`, `expiresAt` (защита от подсовывания старого манифеста);
- список релизов: `version`, `installer` по архитектурам (URL, размер, SHA-256), артефакты продукта, данных и WebUI (URL, размер, SHA-256);
- `minimumSourceVersion` / разрешённые исходные версии;
- `revoked: [версии]` — отозванные релизы не ставятся, а установленные получают предложение обновиться;
- `rollout`: доля роутеров (детерминированно по хешу ID установки);
- подпись манифеста отдельным файлом.

Ключ подписи хранится офлайн; ключи будущей поддержки и любых других функций — отдельные.

## 5. Раскладка на устройстве

```text
/opt/broray/launcher/           загрузчик (вне версий)
/opt/broray/versions/<v>/       не более двух версий: текущая и предыдущая
/opt/broray/current -> versions/<v>   атомарная замена симлинка
/opt/broray/config/config.v<N>  конфигурация по версии схемы; предыдущая копия хранится до подтверждения
/opt/broray/data/               подписки, серверы, каталоги маршрутов
/opt/broray/state/              журнал операции, health, ID установки
/opt/broray/run/                сокет управления, lock-файл демона
```

Бюджет места: на KN-1811 после резервной копии свободно ~61 МБ `/opt`. Две версии одного multi-call бинарника, данные и временный архив обновления должны укладываться с запасом; точный бюджет фиксирует Task 0 по измерениям.

## 6. Остановка демона без PID

Ядро 4.9 на целевых роутерах не даёт pidfd. Демон всё время жизни держит эксклюзивный `flock` на `/opt/broray/run/brorayd.lock`.

1. Обновитель подключается к Unix-сокету демона и отправляет аутентифицированную команду `shutdown` (токен из `state/`, права 0600).
2. Ждёт возможности взять тот же `flock` с таймаутом. Ядро снимает блокировку только при завершении процесса, поэтому повторное использование PID и «живой/мёртвый» не возникают.
3. Если демон не ответил на сокет или не освободил lock за отведённое время — операция отказывает, ничего не меняет и сохраняет диагностику. Принудительный `kill` по PID запрещён.

## 7. Последовательность обновления

1. Проверить манифест, совместимость, место.
2. Скачать и проверить все артефакты во временный каталог; распаковать безопасно (без абсолютных путей, `..`, ссылок за пределы).
3. Записать в журнал `prepared`.
4. Разложить новую версию в `versions/<new>/`; мигрировать конфиг в `config.v<N+1>`, старая копия остаётся.
5. Журнал `stopping` → остановить демон (§6).
6. Журнал `switching` → атомарно заменить `current`.
7. Запустить демон; он должен подтвердить готовность через сокет за отведённое время.
8. Успех → журнал `committed`, удалить версию старше предыдущей. Неудача → откат: `current` назад, старый конфиг, запуск старого демона, журнал `rolled-back`.

**Сбой питания:** init-скрипт при старте вызывает `brorayctl recover`, который по журналу доводит операцию до `committed` или откатывает. Состояние после любого сбоя — одна однозначная версия.

**Перезагрузка роутера не запрашивается ни в одном исходе:** установка, обновление, откат, ремонт и удаление. Это часть контракта и проверяется тестами.

## 8. Переход со старого BROray 3.x

Один раз, только из терминала, тем же обновителем в режиме `migrate-legacy`:

1. Read-only экспорт: URL подписок, серверы, пользовательские маршруты, выбранный сервер — в формат 3.5.0, с отчётом о том, что не перенесено.
2. Остановка старых сервисов штатными init-скриптами (интерактивный запуск владельцем допускает штатный `stop`), удаление S22–S28, старого updater и его state после подтверждения пользователя; Entware, сеть и доступ к Keenetic не трогаются.
3. Чистая установка 3.5.0 и импорт экспортированных данных.

Кнопки старых версий для перехода не используются.

## 9. Проверки

- **Корпус состояний:** для каждого опубликованного релиза 3.5.x сохраняется эталонный снимок `config/ data/ state/`. CI прогоняет обновление из каждого снимка в новую версию; релиз не собирается, если хоть одна миграция падает.
- **Внедрение сбоев** на каждом шаге §7 (до/после fsync, до/после rename, до/после health).
- **Тесты загрузчика:** golden-тесты контракта ABI v1; отказ при неверной подписи, просроченном манифесте, отозванной версии, неверной архитектуре, нехватке места, коротком скачивании.
- **Физическая приёмка** на тестовом Keenetic перед каждым stable: чистая установка, обновление, откат по провалу health, сбой питания посередине, `uptime` без сброса.

## 10. Открытые вопросы

- Размер multi-call бинарника на arm64 и итоговый бюджет `/opt` (Task 0).
- Кто и где подписывает манифесты (офлайн-ключ, процедура выпуска).
- Хостинг манифестов и артефактов (`api.brovibe.cloud` или другой) и тестовый канал для KN-1811.
- Служба удалённой поддержки — отложена; при возврате к ней использует собственный ключ и не расширяет контракт загрузчика.
