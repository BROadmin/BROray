# BROray 3.5.0 на Go: чистая установка — Implementation Plan, редакция 2

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` or `superpowers:subagent-driven-development` to implement this plan task-by-task. Делегирование подчиняется `AGENTS.md`: только подтверждённо бесплатные wrappers из `CODEX-TOOLS.md`, без платного fallback. Steps use checkbox (`- [ ]`) syntax for tracking.

**Редакция 2 (2026-11-01), принята владельцем.** Изменения против редакции 1:

1. Один multi-call бинарник вместо семи отдельных: на целевом KN-1811 свободно ~61 МБ `/opt`, семь статических Go-бинарников и две версии рядом не помещаются.
2. Порядок работ — вертикальный срез: рабочий сценарий на физическом роутере раньше инфраструктуры независимых обновлений.
3. Механизм обновления — по `BRORAY-3.5.0-UPDATER-DESIGN.md`: замороженный загрузчик скачивает и запускает обновитель целевой версии; обновитель = установщик = ремонт.
4. Перезагрузка роутера не запрашивается ни в одном сценарии.
5. Однократный переход со старого 3.x: терминальный режим `migrate-legacy` с read-only экспортом подписок, серверов и пользовательских маршрутов.
6. Bogon-сети в каталогах маршрутов всегда отбрасываются.
7. Подпись — формат minisign/Ed25519 с ротацией ключей, без новой схемы.

Выпуск 3.2.1 отменён; revision-12b сохраняется как архивное предложение.

**Goal:** Новая реализация BROray 3.5.0 на Go для чистой установки на Keenetic/Entware с сохранением нужных функций BROray и обновлением, не зависящим от логики установленной версии.

**Architecture:** Один статический multi-call бинарник `broray` (подкоманды `daemon`, `ctl`, `worker <module>`, `installer`, `launcher`). Постоянно работает только `broray daemon`; операции модулей выполняются короткоживущими процессами того же бинарника через ограниченный IPC. Независимо обновляемые артефакты: бинарник, WebUI, каталоги данных маршрутов, внешний Xray. Xray остаётся внешним сетевым движком, WebUI — браузерным HTML/CSS/JavaScript-приложением.

**Tech Stack:** Go и стандартная библиотека; минимальный набор закреплённых зависимостей (minisign-проверка, авторизация Keenetic); JSON, Unix sockets/stdio IPC, штатные интерфейсы Keenetic. Сборка `CGO_ENABLED=0`, если Task 0 подтверждает её на цели.

**Spec:** Требования владельца: BROray 3.5.0; готовые маршруты Claude и Netflix; отдельные обновления; Go; чистая установка; без перезагрузок; обновление не должно повторять проблемы 3.x. Источники маршрутов — `docs/DEVELOPMENT-PLAN.md`. Механизм обновления — `BRORAY-3.5.0-UPDATER-DESIGN.md`.

**Исполнитель:** Claude. Документ — задание для разработки и ревью; Go-реализация на момент написания отсутствует.

## Global Constraints

- **Никаких перезагрузок:** установка, обновление, откат, ремонт, переход с 3.x и удаление никогда не запрашивают и не выполняют перезагрузку роутера. Проверяется тестами и физической приёмкой (`uptime` без сброса).
- Новая версия ставится на чистую Entware. Если найден старый BROray, установщик отказывает и предлагает режим `migrate-legacy` (терминал, явное подтверждение владельца). Автоматического удаления нет.
- Разработка в `implementation/go/` на предусмотренной ветке. `implementation/runtime/` — источник требований и регрессионных примеров; `implementation/root/` и корневой `root/` не являются источником релиза. `references/3.1.0-r09c02/` и завершённые checkpoint-артефакты не изменять.
- Перед каждым этапом — обзор `docs/ERROR-REGISTER.md`, связанных findings и текущего журнала по `AGENTS.md`. Реальные ошибки инструментов, команд, harness и продукта записываются; первая неудача остаётся доказательством.
- Идентичность процесса: не PID. Демон держит `flock` на `run/brorayd.lock` всё время жизни; остановка — команда через собственный сокет и ожидание освобождения lock. `kill` по PID запрещён; возраст блокировки не разрешает её удалить.
- Чистая установка сохраняет Entware, сеть, доступ к Keenetic и посторонние данные.
- Первый целевой профиль — `linux/arm64`, Keenetic aarch64/Entware aarch64-3.10. Другие архитектуры (в том числе MIPS) не поддерживаются, пока не пройдут отдельные проверки; установщик сообщает об этом явно, а не отказывает молча.
- Каталоги маршрутов: bogon-сети (RFC 1918, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `0.0.0.0/8`, `224.0.0.0/4`, `240.0.0.0/4` и аналоги IPv6) всегда отбрасываются с записью в отчёт.
- Уровни доказательств: локальные тесты, VM и физический Keenetic различаются. Перед release candidate — `ERROR-REGISTER-REVIEW.json`; публикация и Stable — собственные gates и авторизация.

## Review Focus

1. Потеря питания между сменой версии и подтверждением health: однозначная рабочая версия после старта, без смешанных бинарников и конфигураций. Tasks 4, 9.
2. Несовместимые WebUI, данные или конфиг: отказ до изменения активного состояния с понятной причиной. Tasks 1, 4, 7.
3. Отмена, зависание, параллельная операция: нельзя завершить чужой процесс, удалить неоднозначную блокировку или начать вторую мутацию. Tasks 3, 4.
4. Источники маршрутов: пробелы, широкие и bogon-сети, дубли, повреждённый источник — предсказуемый результат и сохранение рабочего набора. Tasks 2, 6.
5. Нехватка RAM/диска и особенности Entware: предсказуемый отказ, сохранённый административный доступ; host PASS не подменяет target PASS. Tasks 0, 4, 9.

## 1. Что строить

Новая управляющая реализация, а не перевод shell-файлов на Go. Существующий код — источник функциональных требований и доказанных решений; открытые дефекты не копировать. Матрица паритета отделяет согласованные функции от исторических случайностей.

Обязательная матрица: авторизация и сессии WebUI, доступ Keenetic/KeenDNS; установка и управление Xray, выбранный сервер, проверка конфигурации, запуск и восстановление; серверы, подписки, согласованные форматы импорта; готовые и пользовательские маршруты и их реальное состояние на Keenetic; DNS и связь с Keenetic; операции, прогресс, отмена, диагностика, обновление и удаление BROray; готовые наборы **Claude** и **Netflix**.

Новые протоколы, второй сетевой движок, универсальный YAML-движок и импорт чужих глобальных настроек в 3.5.0 не входят без отдельного требования. Служба удалённой поддержки отложена.

## 2. Архитектура

| Единица поставки | Состав | Обновление |
| --- | --- | --- |
| Бинарник `broray` | daemon, ctl, workers (xray, servers, subscriptions, routes, dns), installer, launcher | целиком, через обновитель; модули внутри объявляют версии и схемы данных |
| WebUI | статические файлы, совместимые с объявленной версией API | отдельный подписанный артефакт |
| Каталоги маршрутов | данные Claude, Netflix и др. | отдельные подписанные артефакты; refresh одного каталога не трогает остальные |
| Xray | внешний бинарник XTLS | отдельная операция, отдельно от кода управления |

Граница core ↔ worker — тот же IPC-контракт, что в редакции 1 (`workerProtocol=1`): worker запускается как `broray worker <module>` с operation ID и ограниченными параметрами. Это сохраняет возможность позже вынести модуль в отдельный бинарник без изменения протокола.

## 3. Структура исходников (`implementation/go/`)

```text
go.mod, go.sum, toolchain.lock
cmd/broray/main.go            # multi-call: daemon | ctl | worker | installer | launcher
internal/contracts/           # схемы, типы API/IPC, совместимость
internal/platform/            # конфиг, журнал, операции, flock-guards
internal/keenetic/            # типизированный адаптер штатных интерфейсов
internal/auth/                # авторизация, сессии, защита запросов
internal/ipc/                 # ограниченный протокол workers
internal/launcher/            # замороженный загрузчик ABI v1 + golden-тесты
internal/installer/           # установка, обновление, ремонт, migrate-legacy
modules/{xray,servers,subscriptions,routes,dns}/
webui/
schemas/                      # API, worker protocol, manifest канала, конфиг
tests/fixtures/  tests/integration/  tests/state-corpus/
scripts/build-target.ps1  scripts/verify-plan-artifacts.ps1
docs/                         # ADR, API, паритет, измеренные бюджеты
```

## 4. Обновление

Полностью по `BRORAY-3.5.0-UPDATER-DESIGN.md`: замороженный загрузчик ABI v1; обновитель целевой версии; раскладка `versions/<v>` (не больше двух) + `current` + `config.v<N>`; остановка через сокет и `flock`; health-подтверждение; автоматический откат; `brorayctl recover` по журналу после сбоя питания; манифест канала с `expiresAt`, `revoked`, `rollout`; minisign/Ed25519 с ротацией; корпус состояний всех релизов в CI.

## 5. План работ

Каждый этап: RED → минимальная реализация → GREEN; требуемая неудачная проверка блокирует переход. `go test` — из `implementation/go/` после закрепления toolchain.

### Task 0. Пригодность Go на физическом Keenetic и бюджеты

- [ ] Матрица паритета `docs/FUNCTIONAL-PARITY.md`: сценарий → источник требования → состояние в 3.x → проверка.
- [ ] Закрепить реально проверенный Go (`GOTOOLCHAIN=local`), `GOOS=linux GOARCH=arm64`, `CGO_ENABLED=0`; проверить ELF без динамических зависимостей.
- [ ] Probe-бинарник на **физическом** тестовом Keenetic (по разрешению владельца, read-only к системе): TLS/CA, DNS, entropy, часы, Unix-сокет, `flock`, fsync+rename на UBIFS, авторизация Keenetic, размер RSS.
- [ ] Измерить размер multi-call бинарника (`-s -w`), RSS демона в покое и пике worker; зафиксировать бюджет `/opt` для двух версий + данных + временного архива.

**Gate:** target receipt, паритет, бюджеты. Если Go на цели не работает или бюджет не выдержан — остановка с конкретным выводом.

### Task 1. Контракты и схемы

- [ ] `internal/contracts`, `schemas/` (API v1, worker protocol v1, конфиг, манифест канала), `docs/ADR-001`.
- [ ] RED: дублирующиеся JSON-ключи, неизвестный ABI, неверная архитектура, несовместимая схема данных, неверная подпись манифеста.
- [ ] `go test ./internal/contracts -count=1`.

**Gate:** контракты зафиксированы; модули не изобретают свои поля.

### Task 2. Вертикальный срез MVP на роутере

Минимальный рабочий продукт целиком, без независимых обновлений:

- [ ] `broray daemon`: API v1, авторизация (правила `ndw4auth`, фикстуры `R67C02…R67C03`), статус.
- [ ] servers + subscriptions (URI/Base64/Xray JSON) → конфиг → Xray (внешний бинарник) → штатная интеграция Keenetic.
- [ ] routes: каталоги Claude (`Global/ AI_Claude`, с сохранением ведущего пробела) и Netflix (два `.bat`), разбор как данных, bogon-фильтр, план → применение → фактическое состояние.
- [ ] Минимальный WebUI: вход, сервер, подписка, маршруты, статус.
- [ ] `broray installer install` для чистой Entware (без механизма обновления).
- [ ] RED: чистая установка без Claude/Netflix, потеря пробела Claude, `100.64.0.0/10` в Netflix, неуспешная проверка Xray, повторная установка с занятым путём.

**Gate:** на физическом тестовом Keenetic с чистой Entware: установка → сервер → маршруты Claude/Netflix работают; `uptime` без сброса; удаление оставляет Entware и сеть нетронутыми.

### Task 3. Операции, журнал, отмена

- [ ] Durable записи операций, одна конфликтующая мутация, `flock`-владение демона, reaping workers.
- [ ] RED: повтор `RequestID`, конкурирующие мутации, отмена до/во время/после commit, смена boot ID, worker exit без terminal event, повторное использование PID.

**Gate:** crash/restart/отмена не дают двойного исполнения и потери владения.

### Task 4. Обновитель по проекту

- [ ] `internal/launcher` (ABI v1, golden-тесты), `internal/installer` (`apply`, `repair`, `recover`).
- [ ] Остановка через сокет + `flock`; переключение `current`; миграция `config.v<N>`; health; автоматический откат; журнал и `recover` при старте.
- [ ] Обновление каталога маршрутов и WebUI без смены бинарника; SHA-256 остальных артефактов неизменны.
- [ ] Корпус состояний `tests/state-corpus/` и прогон «каждый релиз → новый» в CI.
- [ ] Внедрение сбоев на каждом шаге; нехватка места; короткое скачивание; отозванная версия; просроченный манифест.

**Gate:** обновление, откат по провалу health и восстановление после сбоя питания на физическом Keenetic без перезагрузки.

### Task 5. Переход со старого 3.x (`migrate-legacy`)

- [ ] Read-only экспорт подписок, серверов, пользовательских маршрутов и выбранного сервера из state 3.x; отчёт о непереносимом.
- [ ] Остановка старых сервисов штатными init-скриптами при интерактивном запуске владельцем, удаление S22–S28, старого updater и его state после подтверждения; Entware, сеть и доступ Keenetic не трогаются.
- [ ] Фикстуры: compact-5 (`c190e22b…`), r14 (`0ecb69c2…`), r12-платформа (`ac4593ef…`), 3.2.0-r12 на compact-5 (KN-1811), состояния `boot-pending`/`boot-failed`.

**Gate:** с копии `/opt` KN-1811 (DPAPI) в VM — экспорт и чистая установка с импортом; затем физически, по решению владельца.

### Task 6. Маршруты полностью

- [ ] Пользовательские маршруты, обновление/удаление, независимый refresh Claude без изменения Netflix/DNS/Xray.
- [ ] Регрессия `V7_UI_INSTALLED_ROUTE_STATE_DEMOTED_AFTER_REINSTALL` и R66 recurrence.

### Task 7. Подписки полностью и расписание

- [ ] Ограниченный Clash/Mihomo YAML; redirect/таймаут/размер; неполный разбор не заменяет каталог пустым; не применять чужие DNS/правила/порты.

### Task 8. DNS и завершение адаптера Keenetic

- [ ] Typed план, подтверждение фактического результата, ограниченный откат своих изменений; без зависимости от GNU `stat`, jq regex и дробного `sleep`.

### Task 9. WebUI полностью и общая приёмка

- [ ] Версии бинарника, WebUI, каталогов и Xray раздельно; объяснение заблокированных обновлений; старая вкладка после обновления.
- [ ] `go test ./... -count=1`, `go vet`, fuzz парсеров, race.
- [ ] VM: чистая установка, обновления, откат, сбой питания, заполнение диска, `migrate-legacy`.
- [ ] Физическая приёмка на тестовом Keenetic: before/after, байты кандидата, процессы, маршруты, DNS, Xray, ресурсы, административный доступ, `uptime` без сброса.
- [ ] Подписание, публикация и Stable — отдельные разрешённые действия.

**Gate:** все требования матрицы имеют результаты нужного уровня; при физическом отказе release readiness не объявляется.

## 6. Что Claude возвращает после каждого этапа

1. Изменённые файлы и точные идентичности; что выполнено и что осталось решением.
2. Reviewed error IDs, RED → GREEN, регрессии.
3. Команда, exit code, raw receipt и SHA-256 реально сохранённых файлов; провалы сохраняются.
4. Уровень: host / fixture / ARM64 VM / физический Keenetic; target/toolchain identity.
5. Открытые ошибки и решение о следующем шаге; `NOT_RUN` и `UNCONFIRMED` явно.

## 7. Тестовый роутер

KN-1811 (aarch64, KeeneticOS 5.2 Beta 2) сейчас работает с BROray 3.2.0-r12 на legacy-платформе compact-5; полная копия `/opt` сохранена (DPAPI, SHA-256 архива `1d71b793…`). Для чистой установки на нём нужен либо прогон `migrate-legacy` (Task 5), либо отдельное решение владельца о снятии старого BROray до Task 2. До этого решения роутер не изменяется.
