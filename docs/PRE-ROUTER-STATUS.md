# BROray 3.1.1 — подготовка без роутера

Дата: 15.09.2026. Роутер занят другим процессом; доступ к нему запрещён до отдельного сообщения пользователя.

## Назначение комплекта

Это рабочий комплект проектирования, прототипа и проверок. Это **не устанавливаемый кандидат**. Полный объём задания сохранён: операции, блокировки, восстановление, остановка, журнал, диагностика и WebUI. Новые модули пока не подключены к работающим entrypoints, версия runtime остаётся точной базой 3.1.0-r09c02. Отсутствие интеграции явно отделено от проверок алгоритмов.

## Подготовлено

- Изолированная ветка `codex/broray-3.1.1-operations`, точные исходники из проверенного релизного архива; исторический Git `root/` не используется для runtime.
- Воспроизведение дефекта старого reclaimer: пятифайловые system-lock scheduler и auto-switch остаются после исчезновения владельца. Исходный триггер пользовательского сбоя по-прежнему `ROOT_CAUSE_NOT_PROVEN`.
- Карта producers/consumers, дочерних процессов, защищённых фаз и updater fences.
- Прототип ядра Operation Manager в существующем хранилище `operations/`; owner identity, token, state/revision, отмена по запросу, pause/resume, recovery. Старый `last-operation` updater не переназначается.
- Маленький native guard: kernel fcntl, завершение вместе с процессом, атомарная публикация заранее подготовленной ссылки, fsync перед публикацией. Исходник и статические ARM64/Linux 3.10 и x86_64/Linux сборки.
- Единая публичная проекция данных для UI и журнала. Свободные сообщения/URL/config/credentials не принимаются; сообщения берутся из каталога. Ограниченный JSONL-журнал, до 3 × 256 КиБ, выдача до 500 событий.
- Linux-стенд QEMU: без сетевого устройства и без подключённых папок хоста. Тесты не знают адрес роутера. Отдельные проверки реального ядра и синтетических process identities.
- Макет новых блоков WebUI на CSS точной текущей версии; демонстрационные данные, локальные действия, без обращения к API роутера.
- `tests/router-preflight.sh`: подготовленная проверка чтением. **На роутере не запускалась.** Не содержит SSH, записи файлов, сигналов или управления службами.
- Контракт API/отчёта, подробная матрица приёмки и порядок физического прогона.

## Что означает PASS

PASS в локальном отчёте относится только к названному сценарию и к конкретному SHA исходника. Старый Windows-adapter отчёт Stage 02 проверял ранний прототип; новый формат atomic fence проверяется в Linux. Прогон x86_64 QEMU не подтверждает работу ARM64-бинарника на Keenetic, filesystem crash durability, сохранность VPN или готовность обновления.

## Осталось в коде до кандидата

1. Подключить все producers одновременно: routes/API, scheduler, auto-check/auto-switch, Xray worker handoff. Частичное включение не допускается.
2. Завершить begin/ack/retry: потеря ответа coordinator не должна оставлять вечную операцию на PID живого daemon. Сканировать abandoned `starting` без global fence.
3. Связать каждый управляемый child с владельцем **до допуска child к работе**. Падение parent при живом child не разрешает освобождение ресурсов.
4. Вставить cooperative cancellation и heartbeat в реальные циклы. Перед server/subscription commit и Xray activation переключаться в защищённую фазу. Heartbeat перенести в RAM, сохранять state только при изменении фазы.
5. Доказать безопасную адресацию TERM/KILL. В прототипе эскалации **нет**; PID/starttime-check сам по себе не является безопасным process handle.
6. Реализовать отдельный переход со старых пятифайловых lock и supported delivery при уже заблокированном updater 3.1.0. Прототип не удаляет такой lock по PID или возрасту.
7. Включить все события, ограничение operation history и безопасное поведение при disk-full/ошибке ротации. Сейчас потеря записи события не блокирует безопасное завершение операции; состояние полноты журнала ещё нужно выводить в отчёт.
8. Подключить authenticated CGI и фактические snapshots сервисов к отчёту; макет не подменяет backend.

Эти пункты нельзя пометить выполненными только потому, что роутер ещё недоступен. Подготовка делает решения и проверки воспроизводимыми; продуктовая интеграция и приёмка остаются отдельными этапами.

## После освобождения роутера

Сначала выполнить только подготовленный preflight и сохранить очищенный отчёт. Затем сверить архитектуру/ядро/базу и доступный способ доставки, закрыть оставшиеся пункты интеграции, собрать уникальный кандидат, показать его manifest и план установки. Только после этого переходить к установке и физическим тестам по `ROUTER-TEST-PLAN.md`.

Никаких публикаций, установки или изменения конфигурации роутера этим комплектом не выполнялось.
