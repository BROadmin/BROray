# BROray 3.5.0 — паритет функций с 3.x (3.2.0-r12, f505928)

Основная матрица ниже описывает базу dev5. Локальные изменения исходников dev6 и их отдельные
квитанции приведены в последнем разделе. Проверки dev6 в VM не считаются проверками на KN-1811.

Принцип: страницы, стили и скрипты WebUI 3.x отдаются **без изменений** (кроме метки сборки
`WebUI-3.5.0-dev5` и списка готовых маршрутов), а демон Go обслуживает все URL `/api/**/*.cgi`
с контрактами 3.x: метод, параметры, тело, порядок проверок, HTTP-коды, коды ошибок, русские
тексты, форма успешного ответа, побочные эффекты, фоновые задачи. Контракты извлечены из кода 3.x
со ссылками файл:строка: `docs/contracts/*.md`.

## Сознательные отличия от 3.x

**Продуктовые решения владельца**
1. Готовые маршруты — один алфавитный список из 12 наборов (10 из 3.x + Claude и Netflix), без «рекомендуемых»/«extended». Для Claude и Netflix — нейтральные значки-монограммы.
2. Xray — одна копия `/opt/broray/runtime/xray`. Как в 3.x, владелец выбирает на странице «Xray» любую **официальную** версию XTLS (каталог GitHub: 2 последних стабильных + 5 предварительных, плюс установленная и проверенная со сборкой); архив — только официальный ассет `github.com/XTLS/Xray-core/releases/download/<tag>/Xray-linux-<arch>.zip`, SHA-256 — из GitHub (поле `digest` API или официальный `.dgst`), перед установкой релиз и контрольная сумма подтверждаются повторно. Пользователю сообщается только совместимость с текущей сборкой BROray: «Совместима с BROray» / «Частично совместима с BROray» (с ограничениями) / «Совместимость не проверялась»; для непроверенной, частично совместимой, предварительной версии и понижения нужно подтверждение. Реестр совместимости встроен в сборку (на dev4 — v26.10.31 для 4 архитектур). Отличие от 3.x: каталог строится для архитектуры роутера (aarch64, armv7, mipsel, mips), 3.x — только arm64.
3. 3.x поставлял Xray внутри пакета; 3.5.0 при первом запуске демона сам скачивает проверенную со сборкой версию (v26.10.31, SHA-256 встроен, без обращения к API GitHub; повтор 30 с → 10 мин). Страница Xray также показывает каталог, если Xray ещё не установлен.
4. Страница «О BROray» работает поверх установщика 3.5.0 (нет opkg-слота и updater-v5). Обновление — через подписанный канал (docs/RELEASE-CHANNEL.md): «Проверить обновления» проверяет манифест канала (minisign/Ed25519, встроенные ключи, срок действия, отзыв, архитектура), без настроенного канала честно отвечает 503 `CHANNEL_UNAVAILABLE` «Канал обновлений не настроен.»; «Установить обновление» и «Переустановить» запускают загрузчик установленной версии и установщик целевой (`versions/<v>`, атомарная смена `current`, остановка демона через сокет без PID, проверка готовности, откат), прогресс — в «Последней операции»; `restore.cgi` завершает прерванное обновление по журналу, иначе прежний 409. Перезагрузка не требуется ни в одном исходе. Удаление — фоновое задание: квитанционное снятие объектов Keenetic всех областей → передача установщику (демон останавливается последним; при сбое ничего не удаляется, демон перезапускается).

**Исправления дефектов 3.x**
5. `resume.cgi` (продолжение прерванной операции с маршрутами) работает; в 3.x он всегда отвечал `ROUTES_API_LOCK_FAILED`.
6. `summary.cgi?bundleId=` работает (в 3.x падал под `set -u`); удаление неустановленного набора — успех, а не 500.
7. Активация сервера: в 3.x на f505928 jq-генератор конфигурации не компилировался; реализован задуманный результат (проверено на 229 ссылках против исправленной копии генератора 3.x).
8. Shadowsocks из Xray JSON в подписках кодируется так, что его принимает собственный разборщик (в 3.x — нет).
9. Сводки: `actionRequired`, `operationRunning` и т. п. отражают реальное значение (в 3.x jq `//` превращал `false` в `true`).
10. Владение ProxyN проверяется по адресу из квитанции: смена LAN-IP/порта больше не делает интерфейс «чужим», «Исправить» переносит upstream.
11. Сравнение running/startup игнорирует все строки-комментарии `!` (RCI отдаёт их иначе, чем ndmc).

**Следствия перехода на один процесс Go**
12. Нет lighttpd, CGI, jq, shell-хелперов, init-скриптов служб: службы 3.x — горутины демона; «PID службы» в отчётах — PID демона.
13. Токены (предпросмотр, preflight, очистка) — случайные; хеши подтверждений считаются в Go (детерминированный аналог `jq -cS`).
14. «Проверить все серверы» — один этап очереди; срочная проверка активного сервера ждёт его окончания.
15. При старте демона записи в состоянии «выполняется» без живой операции помечаются прерванными.
16. Запуск Xray при старте — только при наличии активного сервера (в 3.x — при наличии config.json).
17. Вход: сохраняются коды 3.5.0 (`KEENETIC_ADMIN_RIGHTS_REQUIRED`, `KEENETIC_AUTH_UNSUPPORTED`, …), NDW2/NDW4 из BROmihomo; вместо задержки 1 с после ошибки — счётчик неудач.

## Не перенесено (по решению)
- Удалённая поддержка — отложена.
- Обновление через opkg-слот/updater 3.x — заменено загрузчиком и установщиком 3.5.0 (docs/BRORAY-3.5.0-UPDATER-DESIGN.md, docs/RELEASE-CHANNEL.md). Повтор проверки через SOCKS Xray (3.x) не перенесён.

## Открытые вопросы (проверяются на KN-1811)
- Запись через RCI `127.0.0.1:79` (ADR-002) и разбор `show dns-proxy`/`show interface` в RCI-форме против ndmc-текста.

## Исправления по проверке dev3 на KN-1811 (dev4)
- Запуск: init-скрипт вызывает `broray start` — бинарник сам уходит в отдельную сессию (BusyBox на роутере без `setsid`).
- Чтение `running-config`/`startup-config` — через `ndmc`, если он есть (как в 3.x); запись — пакетами RCI. Раньше сохранение перед установкой маршрутов сравнивало RCI-вывод с ndmc-выводом и не сходилось (`ROUTES_EXPORT_FAILED`).
- `config/system/server-auto-switch.json` создаётся из seed 3.x при первом запуске (раньше первая проверка активного сервера давала `STATE_UNAVAILABLE`).
- Удаление: снятие публикации KeenDNS перенесено в конец (после ProxyN, Xray), чтобы страница, открытая через KeenDNS, показывала ход до последнего этапа; журнал установщика пишется с отметками времени в `/opt/var/log/broray-uninstall-*.log` и переживает перезагрузку.
- Подписки: в предупреждении об отклонённом узле указывается схема ссылки (`для протокола tuic отсутствует импортёр`), сама ссылка не выводится.
- Сборка: зависимости в `vendor/`, `go.work` с локальными путями удалён.
- Совпадение ручного сервера с сервером подписки (две карточки) — поведение 3.x: подписка не сравнивается с ручными серверами.

## UDP через ProxyN (dev5, отличие от 3.x)
- 3.x и 3.5.0-dev1…dev4 создавали ProxyN без `proxy socks5-udp`: в SOCKS-инбаунде Xray `udp:true`, но KeeneticOS по умолчанию не передаёт UDP интерфейса Proxy через SOCKS5 UDP ASSOCIATE. Звонки (WebRTC/VoIP), QUIC и прочий UDP к сетям из наборов маршрутов не шли через BROray.
- dev5: при создании `interface ProxyN proxy socks5-udp` сразу после `proxy protocol socks5`; «Исправить», восстановление после перезагрузки и согласование включают UDP у своего ProxyN на месте (квитанция владения прежняя, SHA блока без строки UDP); откат возвращает прежний режим UDP. Чужие интерфейсы не трогаются.
- Статус Keenetic: `socks5UdpEnabled`, проверка «UDP через SOCKS5», причина `PROXY_SOCKS5_UDP_DISABLED`; в отчёте `runtimeDetails.proxyInterface.socks5UdpEnabled`.
- KeeneticOS до 4.1 не знает `proxy socks5-udp`: если шаг отклонён как неизвестная команда («no such command»/«unknown command»), BROray записывает `state/keenetic-socks5-udp.json` (`socks5UdpSupported:false` и версия KeeneticOS из `show version`) и оставляет ProxyN TCP-only: создание успешно, `matchesExpected` не требует UDP, причина `PROXY_SOCKS5_UDP_UNSUPPORTED` (warning, `actionRequired:false`), `socks5UdpSupported:false`, согласование не повторяет «Исправить», откат не шлёт `no proxy socks5-udp`. После смены версии KeeneticOS (без известной версии — после перезапуска демона) поддержка проверяется заново. Любая другая ошибка шага UDP — сбой с откатом, как прежде.
- `broray diag udp -routed IP:PORT -direct IP:PORT -socks LAN:2080` — проверка пути UDP запросом STUN (только чтение).
- Форма строки в `running-config` и ограничение «работает только с loopback» (форум Keenetic) не подтверждены на роутере — проверяются на KN-1811.
- «Проверить UDP» на странице Keenetic (рядом с «Проверить подключение к Xray»; доступна, когда управляемый ProxyN создан и подтверждён): фоновая операция `keenetic:check-udp` под глобальной блокировкой (`POST /api/keenetic/check-udp.cgi` → 202 + operationId, `GET /api/keenetic/check-udp-status.cgi` — ход и последний результат, `run/keenetic-udp-check.json`). Части: «UDP через сервер» — STUN через SOCKS Xray (адрес upstream ProxyN), Keenetic не меняется; «UDP через ProxyN» — STUN с роутера на адрес, направленный в ProxyN; сравнение — STUN к другому, никуда не направленному серверу (адрес провайдера). Адреса выхода показываются полностью. Вердикты: «UDP идёт через BROray (выход …)», «UDP идёт мимо VPN — через провайдера (…)», «ProxyN не передаёт UDP», «Сервер не передаёт UDP (Xray SOCKS UDP не ответил)», «Не удалось проверить: …».
- Временный маршрут: если адрес STUN не покрыт ни одним маршрутом, BROray добавляет `ip route <IP> 255.255.255.255 <ProxyN> 1200` только в текущую конфигурацию (без `system configuration save`), проверяет, удаляет `no ip route <IP> 255.255.255.255 <ProxyN>` и проверяет удаление (в том числе при ошибке и отмене). Адрес, уже направленный в ProxyN набором BROray, проверяется как есть; адрес с чужим маршрутом пропускается (следующий кандидат). Только публичные IPv4, только /32 к управляемому ProxyN (отдельная грамматика + общий allowlist маршрутов). Квитанция `run/keenetic-udp-check-route.json` пишется до добавления; оставшийся после сбоя маршрут удаляется при запуске демона и перед следующей проверкой.
- Кандидаты STUN (разрешаются при проверке, IPv4): через сервер/ProxyN — stun.cloudflare.com:3478, stun.l.google.com:19302, stun.nextcloud.com:3478, stun.sipgate.net:3478; напрямую — stun.nextcloud.com, stun.sipgate.net, stun.l.google.com, stun.cloudflare.com (Google STUN не ответил напрямую с KN-1811). Проверка на KN-1811 ещё не выполнена.

## Предупреждение об IPv6 (решение владельца, 3.5.0)
- Наборы маршрутов только IPv4 (`ip route … ProxyN 1200`): если провайдер выдал роутеру глобальный IPv6 и он раздаётся в домашний сегмент, трафик сервисов к их AAAA-адресам идёт мимо BROray. BROray только предупреждает — IPv6 не выключает и настройки Keenetic ради этого не меняет.
- Определение — только чтение: `show ipv6 addresses`, `show ipv6 prefixes`, `show interface` (RCI JSON, затем текст ndmc), разбор `internal/keenetic/ipv6.go`; глобальный адрес — 2000::/3 (не fe80::/10, не ULA fc00::/7). Ошибка или нечитаемый ответ — `unknown`, предупреждения нет. Кэш 5 мин (`unknown` — повтор через 1 мин).
- Поле `ipv6: {state: global|none|unknown, wan: [...], lanPrefix, warning, checkedAt}` (добавлено) в `keenetic/status.cgi` (и снимке главной) и `routes/overview.cgi`; на здоровье/severity не влияет. Главная и «Маршруты → Обзор» показывают предупреждение только при `global`.
- Форма вывода KeeneticOS для IPv6 не подтверждена на роутере (образцы в тестах помечены как предполагаемые) — проверить на KN-1811 с включённым IPv6.
## Плановое обновление готовых маршрутов (3.5.0, решение владельца 2026-11-02)
- Базовая версия каталога — закреплённый коммит `65a895d` (SHA-256, размер и git-SHA каждого файла в сборке). На странице «Готовые маршруты» владелец включает проверку обновлений: не проверять (по умолчанию) / 6 ч / 12 ч / сутки / неделя; «Проверить сейчас»; «Устанавливать обновления автоматически» (выключено по умолчанию); порог «не обновлять автоматически, если удаляется больше 25/50/75 %» (по умолчанию 50 %).
- Проверка: `api.github.com` — последний коммит ветки `main` и список .bat каждого каталога (как обнаружение «all-bat» в 3.x); файлы — `raw.githubusercontent.com` на этом коммите, сверка размера и git-SHA из списка, тот же разбор BAT, отбрасывание частных сетей и лимиты, что и при ручной проверке. Хосты фиксированы, адресов из настроек нет. Если API недоступен, ничего не меняется: используется закреплённый или последний принятый список.
- Установленный набор: новая версия скачивается и подготавливается (только чтение Keenetic) — карточка «Готово обновление» с числом добавленных/удалённых маршрутов. Проверенный, но не установленный набор: обновляется только «доступная версия». Не проверявшийся набор не трогается (первая ручная проверка берёт новый список).
- Автоустановка — обычный экспорт (fence, preflight, квитанции, откат) отдельной операцией с источником `SCHEDULER` в журнале BROray; не запускается во время другой операции (повтор через 5 мин), при остановленных фоновых операциях и в режиме обслуживания; неудачная (откатанная) автоустановка не повторяется.
- «Требует проверки»: обновление, удаляющее больше порога установленных маршрутов, или файлы, не прошедшие проверку (строки с ошибками показываются), не применяются автоматически; владелец решает вручную («Скачать обновление» / «Обновить в Keenetic»).
- Файлы: `routes/catalog-schedule.json` (настройки), `routes/catalog-schedule-status.json` (последний результат, 20 последних автоматических изменений), `routes/catalog-remote.json` (принятые списки файлов), поле `scheduledUpdate` в состоянии набора (добавлено к форме 3.x).
## Резервная копия настроек (новое в 3.5.0, страница «BROray»)
- Карточка «Резервная копия настроек»: «Скачать резервную копию» и «Восстановить из файла». Эндпоинты (новые, контракты 3.x не меняются): `POST /api/broray/backup-export.cgi` (файл), `backup-preview.cgi`, `backup-import.cgi`, `backup-undo.cgi`, `GET backup-status.cgi`; POST требуют `X-BROray-Request: 1` и Origin своего хоста. Исправление после dev7 также принимает `X-BROray-Origin` при отсутствии обычного Origin, только для действующей публикации KeenDNS с подтверждённым владением; защита от чужих источников сохраняется.
- Состав: ручные серверы, подписки вместе с их серверами (включённые и выключенные), активный сервер, автовыбор и плановая проверка качества, свои наборы маршрутов (исходные BAT-файлы), id установленных готовых наборов, выбор DoT и его автопроверка, `logLevel`/`health` из config.v1.json. Не входят: квитанции Keenetic, журналы операций, сеансы, логи, кэши, run-состояние, Xray.
- Файл по умолчанию шифруется: PBKDF2-HMAC-SHA256 (600 000 итераций) + AES-256-GCM, заголовок файла — дополнительные данные GCM; без шифрования — только с явным подтверждением. Формат описан в `areas/ops/backupfile.go`.
- Восстановление: проверка файла областями их же валидаторами → предпросмотр (добавить/заменить/удалить) → подтверждение токеном предпросмотра → под глобальной блокировкой всё готовится в staging-каталоге и подменяется; заменённые файлы сохраняются в `data/backup/settings-before-import-*` (5 последних), «Отменить последнее восстановление» возвращает их. Объединение по id: серверы и подписки, которых нет в копии, остаются; у восстановленной подписки состав серверов берётся из копии. Активный сервер переподключается штатно (Xray + ProxyN); наборы маршрутов на Keenetic и DoT не применяются автоматически — владелец получает подсказки.

### Дополнение после аппаратного dev7: запуск восстановления из init

В исходниках исправлен разрыв при переустановке той же версии: если процесс прерван между переименованием `broray` в `broray.old` и размещением нового файла, S24 теперь может запустить восстановление из точного предыдущего бинарника. Для этого требуются журнал ABI 1 в состоянии `replace/switching`, совпадение текущего каталога, отсутствие ссылок в проверяемых путях и полный SHA-256 предыдущего файла. Файл удерживается открытым дескриптором при проверке и запуске; произвольные резервные файлы не исполняются. Постоянной дополнительной копии бинарника нет. Точные init-шаблоны dev5 и dev7 остаются распознаваемыми, изменённые шаблоны отклоняются.

Первый RED воспроизвёл отказ настоящего S24 с кодом 127. Дополнительные RED выявили подмену родительского каталога после проверки и наследование bootstrap-дескрипторов дочерним процессом восстановления. Исправление удерживает дескрипторы каталогов, читает журнал и предыдущий бинарник относительно них и проверяет неизменность действующих путей. Восстановление запускается через дескриптор родительской оболочки, а в дочерней оболочке дескрипторы 3–8 закрываются до exec: они не переходят в перезапускаемый демон.

Окончательный полный пакет установщика в ARM64 VM дал 76 PASS, включая позднюю подмену каталога и отсутствие наследования дескрипторов. SHA-256, BusyBox sed, дескрипторы каталогов, `test -ef` и исполнение через дескриптор ожидающего родителя отдельно проверены на KN-1811 без изменения служб и конфигурации. Первая неудачная проверка исполнения с редиректом сохранена; на этом BusyBox требуется явная дочерняя оболочка. Исправление ещё не установлено на роутер; аппаратный D4 остаётся обязательным. ## Dev6 Stage B: прерванное обновление и восстановление

В info.cgi добавлено поле recoveryAvailable: true только когда журнал установщика содержит незавершённую операцию и блокировка установщика свободна. restore.cgi повторно проверяет журнал и блокировку в момент POST и запускает штатный ctl recover --restart; он может завершить обновление или вернуть предыдущую версию. Кнопка restore-backup на странице BROray активна только в этом состоянии и пока не выполняется другая операция; подпись и подтверждение теперь называют действие «Завершить прерванное обновление». Старая схема полного восстановления приложения из последней резервной копии не реализована. Импорт резервной копии настроек остаётся отдельным сценарием с предпросмотром.
