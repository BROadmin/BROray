# Службы автоматики: анализ до изменения

Baseline `151bc351312239202f691b684353fef7f6bbf33d`. Воспроизведение сохранено отдельно в `docs/evidence/service-identity-reproducer-20260915`: S28 `status` удаляет неподтверждённые PID/starttime. Проверка сохранности FAIL (ожидаемо); сигналы живым процессам не посылались.

S27 останавливает произвольный PID из файла, S28 повторно проверяет birth, но между проверкой и kill остаётся гонка. S28 также удаляет непроверенный start.lock. Два файла identity публикуются раздельно родителем и самим scheduler. Автоматические циклы уже запускаются отдельными jobs, что позволяет отделить их жизненный цикл от службы.

## Контракт изменения

- Один kernel flock на время жизни daemon. Файл lease никогда не удаляется. Полная identity записывается после exec daemon. При старте неоднозначные старые записи сохраняются и блокируют запуск.
- Короткий отдельный control flock сериализует публикацию identity, остановку и retirement. Guard сохраняется дочерним durable writer при смерти shell.
- Остановка — запись запроса с generation текущего daemon. Нет TERM/KILL по PID-файлу. Daemon завершает текущий цикл и проверяет запрос до следующего цикла и каждую секунду ожидания. Init возвращает pending, если завершение ещё не подтверждено.
- Фоновые jobs закрывают унаследованный descriptor service lease перед exec. Постоянный Xray, запущенный таким job, не должен удерживать lease scheduler. Operation fence остаётся самостоятельной защитой незавершённого job.
- PID/starttime остаются только совместимой проекцией для существующего package service capture; argv daemon остаётся прежним. Они не используются как разрешение на сигнал.
- Status не меняет файлы. Неоднозначное состояние возвращается явно. Единственная запись identity и stop-маркер ограничены одним экземпляром на службу.

Исследованы оба init-скрипта, daemon entry/loops/exit, вызовы S27/S28 в setup, S24 и updater, package service identity capture и оба CGI статуса автоматики. Legacy migration, полный install, protected recovery и prolonged automation остаются отдельными gates.

## Уточнение по fork

Проверка `broray_service_run_job ... &` обнаружила дополнительную ash-обёртку с унаследованным lease. Фактические scheduler используют синхронный вызов функции; на этой схеме восемь проверок прошли, включая смерть daemon при живом job. Тем не менее перед exec добавлена проверка фактического PPID: job должен быть непосредственным ребёнком daemon, иначе запуск отклоняется до работы. Сохранённый FAIL не скрывается; отдельная регрессия проверяет отказ лишней обёртке. PID здесь служит проверкой структуры собственного fork, сигналы по нему не отправляются.

Тестовый Python является subreaper и собирает собственных завершившихся daemon, чтобы задержанная очистка zombie самим стендом не подменяла поведение init на роутере. Проверка выжившего helper использует `Popen.wait()` для смерти родителя, затем kernel lease probe, затем разрешает завершение helper. Ожидание EOF вывода до lease probe было исправлено как ошибка порядка harness.

## Stop после аварии и совместимость updater

Физический прогон `physical-services-20260915-04` воспроизвёл остаточный PID/starttime после подтверждённой смерти daemon. Добавлен `retire-dead`: stop получает lifetime flock, затем control flock, повторно проверяет полную identity как STALE и соответствие проекций, удаляет только эти проекции и сохраняет stopped. Такой stop не мешает последующему штатному service capture в updater.

Прогон `physical-services-20260915-03` не доказывает этот новый случай: первоначальный shell assertion использовал AND-list без явного `|| exit 1`, поэтому `set -e` мог пропустить первый отказ. В следующем прогоне assertion исправлен и получен ожидаемый FAIL. Проверки абсолютных путей в общем транспортном harness также разделены на самостоятельные команды до архивации и удаления; прошлые архивы не изменялись.

Сводный Linux-прогон остановился при копировании очередного fixture: накопленные временные приложения исчерпали файловую систему гостя. Это не проверка ENOSPC продукта. Добавлена очистка отдельного service fixture только после подтверждения завершения собственных дочерних процессов. Повторный полный прогон: 29 PASS; результаты закреплены в SERVICE-LIFECYCLE-001.
