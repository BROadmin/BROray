# Диагностический отчёт: заполнение проверяемых фактов

Исходный report всегда возвращает `complete:false`, не читает настройки автоматики и вместо состояний служб выдаёт `unknown`. Координатор, журнал и build metadata уже включены через allowlist. Дефект воспроизведён отдельным локальным тестом: при корректном файле с отключённым автовыбором `automation.autoSwitch` остаётся null. Ожидаемый FAIL сохранён в `docs/evidence/diagnostics-reproducer-20260915` в корне проекта; использован явно отмеченный Windows guard adapter и синтетический owner.

Дальнейшая реализация должна читать только ограниченные локальные факты: три service identity snapshot в изолированных subshell, bool настройки автоматики, ограниченное число конфигураций подписок без URL/имён/credentials, kernel и доверенную cached metadata. Отсутствующий, повреждённый, неоднозначный или слишком большой источник остаётся неизвестным с явной причиной. Пустой доказанный каталог подписок допускает false; неизвестный каталог не означает отключённую автоматику.

В report нельзя вызывать collectors `broray_keenetic_status_json_cached` или `broray_xray_status_json`: при устаревшем кеше они выполняют проверки и записи. Сырые кеши Xray содержат адреса и configCheckOutput, поэтому допустима только явная проекция отдельных полей с признаком возраста. Состояние Xray по кешу не доказывает непрерывность VPN. Вызов service setup меняет OPS_PROC и переменные identity; его необходимо изолировать от текущего coordinator.

Отдельно проверить чтение при readonly filesystem и первом запуске: нынешний client требует уже созданный operations.guard и открывает его на запись. Не менять GET в неявную инициализацию. Эти сценарии требуют воспроизведения до изменения native guard/startup.
