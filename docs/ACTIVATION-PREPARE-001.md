# ACTIVATION-PREPARE-001 — валидация до защищённой активации

## Воспроизведённый дефект

Полный r05c01 на Keenetic Peak: импорт узла успешен, активация
`op-20260915233655-13599-ba2f1d4c4e6f` вернула 503 и оставила stale protected
fence. Реальный Xray 26.9.9 отклонил VLESS без TLS к публичному IP.
`broray_server_activate` входил в committing до генерации и проверки файла;
`BRORAY_JOB_UNRESOLVED=true` не позволял завершить обычную ошибку ввода.

Проверка исходного кода установила, что отказ произошёл до backup, замены
config.json, active-server и перезапуска. На роутере подтверждены прежние
байты конфигурации, сеть и доступ, таблица маршрутов, полная identity Xray и
отсутствие владельца/помощников. Единственное добавление — импортированный
тестовый сервер. Состояние операции архивировано приватно.

Новый Linux-тест сначала воспроизвёл 503 вместо 400 на неизменённом runtime
6bedb4a; это отдельный baseline, не успешный тест.

## Изменение

Активация создаёт закрытый временный каталог операции и выполняет генерацию
и реальную Xray-проверку через зарегистрированный supervisor с лимитом 30 с.
Пока идёт проверка, операция остаётся cooperative/checking. После подтверждённого
завершения всех временных процессов владелец проходит checkpoint committing
и применяет уже проверенный файл. Persistent Xray не запускается под ptrace.

Отказ валидации завершается failed/400 без изменения рабочей конфигурации.
Отмена завершается aborted/409 только после drain. Неподтверждённый drain
сохраняет fence. Ошибка protected restart по-прежнему требует domain recovery.
Общие transaction callers сохраняют прежний путь generate → validate → apply.

Отдельно сохранён protected-путь для вызова с `BRORAY_JOB_UNRESOLVED=true`:
автопереключение использует его при откате уже изменённой конфигурации. Его
валидация не может переводить транзакцию обратно в cooperative/checking.
Отказ при такой проверке оставляет protected/committing для domain recovery.

## Проверки

- `activation-rejection-linux-baseline-20260916`: воспроизведён исходный FAIL.
- `activation-rejection-baseline-20260916-02`: физическое доказательство отказа
  до изменений; первая попытка harness неверно требовала существующий пустой
  registry там, где supervisor ещё никогда не создавался.
- `activation-rejection-recovery-20260916`: точечное test-only восстановление
  завершает только указанную операцию через coordinator finish. Это не
  реализация публичного восстановления произвольной protected-транзакции.
- `physical-activation-prepare-20260916-02`: 4 PASS на ARM с настоящим Xray
  validator, закрытыми бизнес-файлами и stub перезапуска. Первая попытка
  не создала logs в fixture; её отказ и архив сохранены отдельно.
- `physical-activation-prepare-20260916-03`: 5 PASS итогового runtime,
  включая отказ валидации при protected rollback. Namespace архивирован и удалён.
- Расширенная Linux-регрессия фиксируется отдельным итоговым checkpoint.

## Границы результата

Изолированные тесты не доказывают работу полного приложения с VPN-трафиком.
Staging-кандидат и физическое обновление нужны отдельно. Route writers,
общее protected domain recovery, boot recovery, fault matrix и длительный
прогон остаются отдельными открытыми релизными требованиями.
