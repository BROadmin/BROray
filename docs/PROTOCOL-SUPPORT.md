# Протоколы и форматы импорта BROray 3.5.2

Актуально для опубликованного **BROray 3.5.2**, 8 ноября 2026 года. Сверено с [исходниками выпуска v3.5.2](https://github.com/BROadmin/BROray/tree/v3.5.2), commit `b66eb60bcaa56fe5041a19df8efe60e6d07b18c0`. Все таблицы ниже описывают этот выпуск.

Основание Xray: официальный тег **v26.10.31**. Наличие протокола в ядре, наличие импортёра BROray и сохранение всех параметров — разные свойства. Успешный разбор не доказывает работу произвольной комбинации настроек с конкретным провайдером.

## Куда вставлять конфигурацию

- **Одна ссылка сервера** (`vless://`, `socks5://`, `http://` и другие из таблицы): страница **«Серверы»**, поле импорта. Для WireGuard вставьте весь клиентский INI, включая секции `[Interface]` и `[Peer]`.
- **URL подписки провайдера**: страница **«Подписки»**. BROray загружает по этому адресу список ссылок, Base64-список, поддержанный Xray JSON или один клиентский WireGuard INI. Адрес HTTP/HTTPS-прокси и URL подписки вводятся на разных страницах, хотя оба могут начинаться с `https://`.
- **Xray JSON**: поддерживается в ответе подписки — объект профиля с `outbounds` или массив таких объектов. В поле ссылки сервера полный JSON не вставляют. JSON-массив строк ссылок и отдельный объект outbound без `outbounds` не поддерживаются.
- **AmneziaWG**: импортируйте поддержанную ссылку `vpn://` вручную или через список ссылок подписки. Карточка будет иметь пометку **«Только сохранение»**: подключение, проверка качества и автовыбор для неё недоступны.

| ShadowsocksR / Snell | Нет | Нет | Нет |
| OpenVPN / IKEv2 / L2TP / PPTP | Нет | Нет | Нет |

Для AWG в 3.5.2 добавлены разбор и сохранение `vpn://`, **без подключения**. Принимаются поддержанные контейнеры Amnezia с готовой клиентской конфигурацией и Base64-INI с параметрами AWG. Произвольный `vpn://` не считается профилем AWG.

MTProto Proxy не нужен для передачи обычного трафика Telegram через уже работающий VPN. Возможности компонентов Keenetic и других ядер не означают наличия соответствующего backend в Xray/BROray.

Список протоколов Xray подтверждён [реестром inbound/outbound v26.10.31](https://github.com/XTLS/Xray-core/blob/v26.10.31/infra/conf/xray.go), ограничение Hysteria — [его конфигуратором](https://github.com/XTLS/Xray-core/blob/v26.10.31/infra/conf/hysteria.go). Отсутствующие протоколы в таблице отсутствуют в этом реестре. Служебные `direct/freedom`, `block/blackhole`, `dns`, `loopback`, входы TUN/mixed/tunnel не являются дополнительными импортируемыми VPN-серверами.

## Границы разбора

- Подписки: строки ссылок, Base64-список ссылок, поддержанные Xray JSON-профили или один открытый клиентский WireGuard INI. JSON-массив строк ссылок не равнозначен массиву Xray-профилей и не поддерживается.
- Из Xray JSON извлекаются параметры серверов. Чужие routing, DNS, balancers и полный профиль не переносятся как исполняемая конфигурация BROray.
- TLS, REALITY, XHTTP extra и FinalMask имеют разрешённые наборы полей и ограниченные сочетания. `allowInsecure: true` отклоняется. Из `sockopt` принимаются только четыре поля, перечисленные ниже.
- ECH, certificate pinning/name verification, ML-DSA REALITY и VLESS encryption имеют обработчики в коде, но это не обещание всех вариантов этих механизмов.
- Неизвестные query-поля новых ссылок и поля старого VMess JSON дают явную ошибку. Xray JSON проверяется по поддержанной схеме; о непереносимых настройках полного профиля сообщается предупреждением. Успешный импорт не доказывает работу сервера у провайдера.
- Парсерное соответствие старому BROray и тесты генерации конфигураций покрывают конкретные случаи. Полной матрицы «каждый протокол × каждый транспорт × каждое расширение» нет.

Код: [диспетчер импорта](https://github.com/BROadmin/BROray/blob/v3.5.2/areas/servers/build.go), [URL-парсеры](https://github.com/BROadmin/BROray/blob/v3.5.2/areas/servers/parse.go), [валидация записей](https://github.com/BROadmin/BROray/blob/v3.5.2/areas/servers/validate.go), [Xray JSON](https://github.com/BROadmin/BROray/blob/v3.5.2/areas/subscriptions/xrayjson.go), [формат подписки](https://github.com/BROadmin/BROray/blob/v3.5.2/areas/subscriptions/extract.go).

## AmneziaWG: разбор без подключения

Принимается один `amnezia-awg` / `amnezia-awg2` контейнер с `awg.last_config` (JSON-строка), содержащим готовый клиентский INI в `config`. Поддержаны Base64URL/обычный Base64 и Qt qCompress. Также принимается `vpn://` с обычным клиентским INI в Base64: нужны секции Interface/Peer и узнаваемые параметры AWG (например, Jc, H1 или I1). Чистый WireGuard в такой ссылке не объявляется AWG. Сохраняются исходная ссылка, контейнер или отметка формата INI, параметры Interface/Peer, неизвестные расширения. Структура и ключи проверяются; семантика всех AWG-параметров и совместимость с будущим backend не заявляются. Лимиты декодирования и хранения сохранены.

Лимиты парсера: ссылка 64 KiB; распакованный JSON 256 KiB; сохраняемая модель 512 KiB; глубина JSON 64; до 32 пиров и 128 различных полей в секции; строка INI до 16 KiB. Ручная WebUI-форма дополнительно сохраняет прежний предел 16 KiB на одну ссылку, HTTP API — 64 KiB на всё тело запроса. Повторные JSON-поля и неоднозначные контейнеры отклоняются. Не поддержаны импорт голого INI, административные контейнеры без готового клиентского INI, другие протоколы внутри `vpn://` и произвольный многоконтейнерный экспорт.

Валидный AWG принимается в подписку с предупреждением. Удаление/обновление проходят штатную синхронизацию. Повреждённый узел включает существующую защиту неполной подписки. Подключение, проверка качества и выбор AWG в автоматике запрещены; секретные данные не выдаются в summary/details. Нового подключения на роутере эта функция не создаёт.

## WireGuard и расширенные параметры

WireGuard сохраняет PrivateKey, Address, DNS, MTU, Reserved и до 32 Peer с PublicKey, PresharedKey, Endpoint, AllowedIPs, PersistentKeepalive. INI вводится целиком в поле импорта серверов. В JSON используются родные имена Xray (`secretKey`, `remoteDNS`, `keepAlive` и др.). Адрес и порт в карточке берутся из первого пира. Требуются явный клиентский адрес, ключ и endpoint каждого пира. Команды PostUp/PostDown, параметры AWG, неизвестные директивы и `noKernelTun: false` отклоняются. Произвольный WireGuard JSON не запускается как полный профиль.

Параметры транспортов в Xray JSON принимаются в родных блоках. В ссылках добавлено percent-encoded JSON-поле `streamOptions`:

```json
{"wsSettings":{"headers":{"X-Client":"example"},"heartbeatPeriod":30},"sockopt":{"tcpFastOpen":false,"tcpKeepAliveIdle":0,"domainStrategy":"UseIPv4"}}
```

- WS: дополнительные `headers` и `heartbeatPeriod`.
- HTTPUpgrade: дополнительные `headers`.
- gRPC: `idle_timeout`, `health_check_timeout`, `permit_without_stream`, `initial_windows_size`, `user_agent`.
- sockopt: `tcpFastOpen`, `tcpKeepAliveIdle`, `tcpKeepAliveInterval`, `domainStrategy`; остальные поля отклоняются.
- Host задаётся основным полем `host`. В Xray JSON заголовок Host нормализуется в это поле; конфликт с явным host отклоняется. В `streamOptions.headers` Host запрещён.
- Сохраняются `false` и `0`. CR/LF, неверные имена HTTP-заголовков, неоднозначные поля и неизвестные настройки отклоняются. Настройки с потенциальными секретами скрыты из публичного details API.
- `x_padding_bytes` нормализуется в XHTTP `extra.xPaddingBytes`; конфликт значений отклоняется. Непустой `extra` вне XHTTP отклоняется, включая старый бессмысленный вариант `extra=0`.
- Для новых импортов неизвестные query-поля и поля старого VMess JSON дают явную ошибку. Служебный `support-x25519mlkem768` сопровождается предупреждением; его значение не исполняется. При импорте Xray JSON предупреждение перечисляет непереносимые настройки профиля и служебные поля.

Это не обещание произвольных сочетаний всех возможностей Xray. Сохраняются прежние ограничения TLS/REALITY/FinalMask и XHTTP extra. В частности, HTTP proxy-specific headers, произвольные socket options, SIP003-плагины, MASQUE/XDRIVE, TUIC и MTProto в этот пакет не входят. JSON-профили проходят существующий путь импорта подписок, а не вставку полного профиля в поле URI.

Границы приёмки приведены в [описании выпуска 3.5.2](https://github.com/BROadmin/BROray/blob/main/docs/RELEASE-3.5.2.md): четыре архитектуры проверены в изолированной VM, аппаратная проверка выполнена на KN-1811. Разбор всех вариантов конфигураций не означает проверку трафика каждого протокола с любым сервером.

## Синхронизация в 3.5.2

SNI/ShortID могут меняться у одного узла. Внутри одной подписки сохраняется ID при однозначной ротации, накопленные совпадающие по прочим параметрам копии объединяются. Ручные источники и другие подписки остаются независимыми. Исчезновение активного узла по полному ответу удаляет его из каталога и прекращает старое подключение; включённый автовыбор ищет замену по своим настройкам. Неразобранный/повреждённый ответ не доказывает удаления узлов.
