# BROray 3.5.3 — требования к выпуску

Дата: 10 ноября 2026. Статус: планирование, реализация и приёмка 3.5.3 не начаты.

Основа кода: BROray 3.5.2, commit `b66eb60bcaa56fe5041a19df8efe60e6d07b18c0`. Основа схем Xray: официальный тег `v26.11.9`. Если основание меняется, сначала пересчитать затронутые требования и проверки.

## Цель

Принять Xray 26.11.9, устранить молчаливую потерю параметров, добавить подключение через XDRIVE и MASQUE, сохранить обновление с BROray 3.5.0–3.5.2 и доступность управления при отказе VPN.

«Поддерживается» означает: параметр разобран, проверен, сохранён, восстановлен из резервной копии и передан ядру с тем же смыслом. Сам факт успешного импорта не является доказательством рабочего подключения. Полнота относится к опубликованной матрице клиентских профилей; серверные inbound, чужая маршрутизация, DNS, API и управление процессами из импортируемого полного профиля не исполняются.

## Требования

| Код | Требование | Условие завершения |
|---|---|---|
| R1 | Поддержка Xray 26.11.9 | Официальные архивы четырёх архитектур сверены по SHA-256; конфигурации и трафик проверены; метки совместимости соответствуют уровню доказательств |
| R2 | Ни одно входное поле не пропадает молча | У каждого поля URI/JSON/INI есть результат: применяется, преобразуется эквивалентно, отклоняется или явно обозначено как неисполняемые метаданные |
| R3 | Однозначная нормализация | Конфликтующие альтернативные имена дают ошибку; одинаковые значения после предусмотренной нормализации допускаются; повтор одного URI-ключа остаётся ошибкой |
| R4 | Сохранение семантики | Различаются отсутствие, пустая строка, `false`, `0`, пустой список и явное значение по умолчанию; допустимые преобразования перечислены в матрице |

## Границы поддержки и принятые решения

- Сохраняются Go и существующая архитектура BROray; второе VPN-ядро не добавляется.
- Обновление 3.5.x сохраняет данные; переход с 3.2 по-прежнему требует чистой установки. Установка Go на роутер не нужна.
- Повторный вход после обновления, маршруты без `auto`, TCP-only с предупреждением на прошивках без UDP ProxyN остаются согласованным поведением.
- AmneziaWG остаётся «Только сохранение». TUIC/MTProto и другие отсутствующие в целевом Xray backend не объявляются работающими.
- Xray обновляется независимо от BROray. Новые профили имеют проверяемые требования к версии ядра; для новых XDRIVE/MASQUE-профилей 3.5.3 начальное поддержанное основание — 26.11.9. Это продуктовая граница проверки, а не утверждение, что MASQUE появился только в этом релизе.
- Новый закреплённый Xray становится выбором чистой установки после приёмки. Обновление BROray само по себе не заменяет выбранное пользователем работающее ядро.
- `chrome` остаётся динамическим профилем ядра; явно заданный иной отпечаток не заменяется. `hellochrome_155` требует подходящей версии ядра.
- Существующие записи не пересоздаются из исходного URI при обновлении. Новая строгая проверка действует на новые входные данные; старые корректно работавшие сохранённые модели сохраняют поведение. Неоднозначные старые записи получают предупреждение без автоматической смены endpoint/учётной записи.

## Исправления парсера

Исходные находки установлены чтением кода, не отдельным runtime-прогоном. Сначала требуются независимые RED-примеры; ошибочную гипотезу отметить как опровергнутую, не менять код ради ожидаемого результата.

1. Trojan URI: непустые/неприменимые `flow` и `encryption` не должны приниматься общим списком и затем теряться.
2. VLESS URI: `authority` вне gRPC должен давать явную ошибку; тот же принцип проверить для `serviceName`, `mode`, TLS/REALITY-полей вне соответствующего транспорта/защиты.
3. Legacy VMess JSON: проверить пары `add/address`, `id/uuid`, `sni/serverName`, `fp/fingerprint`, `net/network`, `tls/security`, `pbk/publicKey`, `sid/shortId`, остальные перечисленные в парсере альтернативы. Конфликт не разрешать молчаливым выбором первого поля.
4. Hysteria2 `udpIdleTimeout`: сверить с целевым Xray; в теге 26.11.9 допустимы `0` либо целые `2..600`. BROray сейчас проверяет более широкий non-negative int32. Добавить случаи отсутствия, 0, 1, 2, 600, 601, отрицательного и неверного типа.
5. Провести такую же сверку типов, диапазонов, альтернативных имён и взаимных ограничений для всех строк новой матрицы. Не называть непроверенную ветвь корректной по аналогии.

Матрица содержит: формат, протокол, транспорт, защиту, путь поля, тип/границы, правило нормализации, путь в Record, путь в итоговом Xray JSON, минимальную проверенную версию ядра, результат проверки и ссылку на тест. Поля намеренно неисполняемой части полного профиля перечисляются в предупреждении; ошибка содержит путь поля и причину, без его значения.

## XDRIVE

- XDRIVE является транспортом VLESS. Принимать `network: xdrive` и `xdriveSettings` через родной JSON. Не изобретать несовместимую ссылку `xdrive://`: официального share-формата в рассмотренном выпуске нет.
- Переносить `service`, `remoteFolder`, `secrets`, `segmentBytes`, `flushIntervalMs`, `pollIntervalMs`, `maxPollIntervalMs`, `sessionTtlSeconds`, `concurrency`, `eagerWindowMs`, `holeTimeoutMs`, `template`, `s3`, `xmux`; вложенные поля валидировать по тегу, не пропускать произвольный JSON до исполнения.
- Рассмотреть все четыре backend: `google-drive`, `s3`, `template`, `local`. Импорт и генерация каждого входят в матрицу. Реальная работоспособность каждого отмечается отдельно; один Google Drive PASS не подтверждает остальные.
- Обязательны VLESS Encryption и подходящий включённый Mux; `flow`, REALITY, отрицательные concurrency и `xudpProxyUDP443: skip` для этого транспорта запрещаются согласно ядру. Сочетания TLS/ALPN/FinalMask проверяются отдельно. Обычные XHTTP-профили не получают Mux автоматически.
- Google Drive использует три секрета в определённом порядке: Client ID, Client Secret, Refresh Token. Для `local` запретить импорт произвольных путей файловой системы; допускается только явно выбранный каталог BROray для испытаний, без shell-команд. Для S3/template исключить команды, подстановки окружения и доступ к чужим локальным файлам.
- В UI показать требование одинаковых версий Xray клиента и сервера и статус публичного тестирования XDRIVE upstream. Не обещать нераспознаваемость ТСПУ или заданную скорость.
- Проверка качества измеряет запрос через сам туннель; ICMP до формального endpoint/Google не используется как оценка пути через Drive. Сохранить отдельно длительность установления и измерение прогретого канала. Сохранить действующую политику автовыбора и поиска замены исчезнувшего активного узла: профиль участвует при совместимом ядре и выполнении настроенных условий. Прежний минимальный рейтинг не ослаблять молча; отдельный новый переключатель участия без необходимости не вводить.
- Проверить внешний путь к API/хранилищу при маршрутах через ProxyN, отсутствие петли и сохранность KeenDNS/WebUI. На лимитах API применять ограниченные повторы с паузой; не создавать новый туннель/массовый опрос для каждого фонового тика.

## MASQUE

- Отдельный `protocol: masque`, не разновидность VLESS. Поля `settings`: `address`, `port`, `remoteDNS`. Поля `masqueSettings`: `host`, `path`, `user`, `pass`, `headers`, `warp`, `xmux`; вложенные `warp` — `privateKey`, `publicKey`, `address`.
- Сохранить значения и ограничения TLS/ALPN, разрешённых socket options и FinalMask по целевому ядру. Не выдавать сочетание REALITY+MASQUE за допустимое.
- Запретить сочетание `warp` с user/pass, конфликт явного Authorization с user/pass, запрещённые Host/Capsule-Protocol в headers, неверные ключи, адреса и шаблоны path. Проверки должны совпадать с ядром и не выводить секреты.
- Автоматическая регистрация аккаунтов WARP/облачных сервисов не входит в выпуск. Готовая WARP-конфигурация импортируется; отсутствие реального испытания этого варианта отражается отдельно.

## Приёмка и ограничения работ

**Решение владельца от 10 ноября 2026:** кандидат готовится с явным ограничением обычного WireGuard на MIPS/MIPS LE. Его запуск в эмуляции официального Xray не прошёл; причина и поведение настоящего MIPS-роутера не установлены. Прежние FAIL сохраняются, остальные проверки и этапы обновления/отката/аппаратной приёмки обязательны. Основание: `G:\GPT-Codex\BROray-3.5.3\OWNER-DECISION-WG-MIPS.json`.

- Сначала локальные проверки и offline VM, затем один общий аппаратный цикл кандидата. Проверки отказов используют свои синтетические профили и управляемые тестовые сервисы.
- Архитектуры: aarch64, ARMv7, MIPS little-endian и MIPS big-endian. Эмулятор и настоящий роутер — разные уровни доказательств.
- Для новых сетевых backend необходимы настоящие выделенные тестовые реквизиты/endpoint; при их отсутствии фиксировать конкретный BLOCKED, не выдавать имитацию за публичный сервис.
- Не повторять неизменные D13/полное удаление, шестичасовой цикл и прежние аппаратные сценарии только ради новой версии. Повтор нужен при затрагивающем их изменении или неразрешённом результате.
- Не выполнять перезагрузки, opkg-операции, изменение чужих объектов, полное удаление данных и публикацию в рамках самого составления плана. Будущие действия выполняются в пределах актуального поручения и разрешений владельца; старое разовое разрешение не расширяется автоматически.
- Все P0/P1/P2 в заявленной поддержке блокируют выпуск; P3 учитываются в отчёте. Непроверенные варианты помечаются отдельно и не получают PASS.
